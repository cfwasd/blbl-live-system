## 1. 项目概述

### 1.1 建设目标
构建一套高稳定性、低延迟、可扩展的虚拟 AI 人物直播弹幕驱动系统：
1. **实时数据接入**：通过 Python 管理端接入 B站直播 WebSocket，毫秒级获取弹幕、礼物、SuperChat (SC)、舰长等互动事件。
2. **中心化业务治理**：在管理端实现违禁词过滤、同用户冷却防刷、动态优先级排队、全局限流与配置动态热更新。
3. **轻量化单向推送**：利用 HTTP SSE (Server-Sent Events) 单向推送到前端直播展示页，降低前端复杂度与状态负担。
4. **OBS / 直播姬友好集成**：展示页以纯 Web 方式构建，支持以浏览器源形式直接嵌入 OBS 或 B站直播姬，实现无缝透明合成与渲染。
5. **前瞻性 AI 演进架构**：从协议层与总线层为后续接入大语言模型 (LLM)、流式语音合成 (TTS)、虚拟形象口型与表情驱动预留标准事件扩展点。

### 1.2 设计原则
* **职责分离**：管理端承担“重逻辑”（协议解析、风控过滤、排序限流、状态维护）；前端展示页承担“轻渲染”（事件监听、动画特效、画面绘制）。
* **单向推送**：通过 HTTP SSE 机制，相比 WebSocket 更轻量、天然支持 HTTP/2 复用和浏览器原生自动重连，避免前端反向操控后端的安全隐患。
* **高可恢复性**：具备心跳保活、异常自动重连与客户端退避机制，管理端或网络抖动恢复后前端页面无感自愈。
* **分级降级与背压控制**：设定有界队列与优先级丢弃策略，在突发弹幕洪峰时保核心体验（SC/礼物不丢、普通弹幕限流平滑）。
* **插件化可扩展**：消息总线与事件模型对后续接入 LLM、TTS、Avatar 驱动完全开放解耦。

### 2.2 组件职责矩阵
| 组件 | 核心职责 | 技术实现 |
| :--- | :--- | :--- |
| **弹幕接入层** | 负责直播间房间解析、WebSocket 连接保活、原始消息包拆解反序列化 | `blivedm` + `asyncio` |
| **消息处理管线** | 原始事件规整、黑名单过滤、正则审查、单用户发言冷却、令牌桶全局限流、优先级重排 | 内存过滤器链（Chain of Responsibility） |
| **广播中心** | 管理客户端连接生命周期、有界队列背压管理、消息多路复用扇出分发 | `asyncio.Queue` 集合管理 |
| **SSE 服务端点** | 维持长连接 HTTP 流、定时发送保活心跳、格式化输出 `text/event-stream` 数据 | FastAPI `StreamingResponse` |
| **配置与监控 API** | 提供房间切换、风控规则、冷却参数、展示样式、LLM/TTS 开关的热更新与运行状态查询 | FastAPI RESTful API |
| **直播展示页** | 订阅 SSE 事件，消费事件队列，控制 DOM 浮层、Canvas 特效及虚拟人物交互 | 原生 JS / Vue / React / Pixi.js |
| **OBS / 直播姬** | 宿主渲染环境，捕获浏览器源视口并推流 | 基于 Chromium (CEF) 浏览器源引擎 |

## 3. 数据流与事件规范

### 3.1 主数据流向
```text
B站 WebSocket 原始包 
  ──▶ blivedm 解析为底层消息对象 (DanmakuMessage / GiftMessage 等)
  ──▶ 映射为统一标准化 Event 对象
  ──▶ 违禁词/敏感词/长度/纯表情基础校验（命中则丢弃并记录审计日志）
  ──▶ 单用户发言冷却检查（按 UID 维护发言时间窗口，未过冷却则丢弃）
  ──▶ 全局限流与突发削峰（令牌桶算法）
  ──▶ 计算事件优先级权重（SC > 舰长 > 付费礼物 > 粉丝牌弹幕 > 普通弹幕）
  ──▶ 广播中心将事件分发至各 SSE 客户端的有界缓冲队列
  ──▶ SSE 服务以标准 text/event-stream 协议向推送到前端
  ──▶ 前端 EventSource.addEventListener 捕获对应事件
  ──▶ 前端动效引擎消费事件，完成排队与上屏渲染
```

### 3.2 标准事件协议规范
所有事件遵循统一的 JSON 包装规范，便于管理端和前端统一协议：

```json
{
  "id": "evt_20261103_163301_000001",
  "type": "danmu",
  "ts": 1793694781000,
  "source": "bilibili",
  "payload": {
    "room_id": 123456,
    "uid": 10001,
    "username": "观众A",
    "content": "主播你好，介绍一下你自己",
    "avatar": "https://i0.hdslb.com/bfs/face/xxx.jpg",
    "medal": {
      "name": "头号粉",
      "level": 12,
      "guard_level": 0
    },
    "priority": 50,
    "extra": {}
  }
}
```

#### SSE 传输层输出样例
```http
event: danmu
id: evt_20261103_163301_000001
data: {"id":"evt_20261103_163301_000001","type":"danmu","ts":1793694781000,"payload":{"username":"观众A","content":"主播你好，介绍一下你自己","priority":50}}

```

### 3.3 事件类型清单
| 事件类型 (`type`) | 业务说明 | 阶段定义 |
| :--- | :--- | :--- |
| `danmu` | 普通文字弹幕、表情弹幕 | **MVP 核心** |
| `gift` | 付费道具礼物（银瓜子/金瓜子类） | **MVP 建议** |
| `super_chat` | 醒目留言（付费置顶留言 SC） | **MVP 建议** |
| `guard` | 上舰事件（总督、提督、舰长） | 可选扩展 |
| `system` | 服务端心跳、配置变更通知、状态告警 | **MVP 核心** |
| `llm_reply` | 针对某条弹幕的大模型思考/生成文本 | AI 扩展阶段 |
| `tts_audio` | 合成语音片段音频流或静态资源 URL | AI 扩展阶段 |
| `avatar_cue` | 驱动虚拟人物的口型、表情、肢体动作参数指令 | 表现力扩展阶段 |

## 4. 管理端核心架构实现

### 4.2 消息处理管线设计 (Pipeline)
处理管线应按以下顺序通过责任链链式执行：
1. **标准化转换（Normalize）**：将底层 `DanmakuMessage` 统一收敛为标准 `Event`。
2. **格式与长度校验（Sanitize）**：过滤空字符、超过 `max_content_length` 的文本自动截断或丢弃，纯符号刷屏直接抛弃。
3. **内容风控审查（Banned Words & Regex）**：
   - 快速敏感词检索（采用 Aho-Corasick 多模式匹配算法或 Trie 字典树提高命中性能）。
   - 正则表达式黑名单（针对网址、广告号、微信号等模式）。
4. **单用户冷却（User Cooldown）**：
   - 维护内存滑动窗口或最近发言时间戳哈希表 `Dict[uid, float]`，在指定秒数（如 10s）内同一用户的后续弹幕直接静默丢弃。
   - 自动维护 TTL 清理机制，防止长时间直播导致 UID 缓存泄漏。
5. **动态优先级计算（Priority Scoring）**：
   - `SuperChat`：优先级 100
   - `Guard` (舰长)：优先级 90
   - `Gift` (大额礼物)：优先级 80
   - 带有主播专属高等级粉丝牌的弹幕：优先级 60
   - 普通弹幕：优先级 30
6. **全局背压与分发（Enqueue & Broadcast）**：向广播中心提交，当消费者出现慢消费时保护服务端内存。

## 5. SSE 与前后端通讯设计

### 5.1 订阅接口定义
```http
GET /api/stream?token=<ACCESS_TOKEN> HTTP/1.1
Host: 127.0.0.1:8000
Accept: text/event-stream
Cache-Control: no-cache
Connection: keep-alive
```
* **鉴权机制**：通过 URL Query 传递 `token`，杜绝公网环境或局域网未授权抓流。
* **响应头规范**：必须关闭一切服务端代理缓冲（如 Nginx 的 `X-Accel-Buffering: no`）。

### 5.2 心跳机制与断线自愈
* 服务端启动后台守护协程，固定间隔（如 15 秒）向所有活跃队列投递类型为 `system` 的心跳事件：
  ```json
  {"type":"heartbeat","ts":1793694781000,"status":"connected","clients_count":1}
  ```
* 浏览器端若超过 45 秒未收到任何数据（包括心跳），主动销毁当前 `EventSource` 并启动指数退避重连。

## 6. 前端展示页与 OBS / 直播姬集成规范

### 6.1 前端核心消费设计
前端使用单页轻量架构，不引入高重度框架，确保在 OBS 内置低版本 CEF 引擎中低内存占用运行：
* **数据流与渲染解耦**：使用一个内部数组作为渲染缓冲区，收到 SSE 弹幕放入缓冲区，通过 `requestAnimationFrame` 平滑出屏，避免高频 DOM 操作造成丢帧。
* **内存防护**：最大上屏弹幕条数硬性封顶（如 20 条），超出则平滑移出首项并销毁 DOM 节点。

### 6.2 OBS 浏览器源配置要点
1. **URL**：配置为本地或局域网地址 `http://127.0.0.1:8000/live?token=xxxx`。
2. **分辨率与透明背景**：
   - 宽度 / 高度根据直播工程画布（如 1920x1080 或 1080x1920）设置。
   - CSS 根节点背景设置为 `background: transparent;` 保持完全透明通道。
3. **关键参数开关**：
   - ❌ **取消勾选**【源不可见时关闭（Shutdown source when not visible）】：防止导播切换场景时浏览器源进程被 OBS 杀死，导致 SSE 断开重连丢失事件。
   - ❌ **取消勾选**【场景激活时刷新浏览器（Refresh browser when scene becomes active）】：防止切换场景导致页面重新载入刷新。

## 7. 安全合规与可观测性

1. **直播风控防护**：
   - 输入端敏感词过滤（违禁词库 + 涉政/涉黄/广告正则）。
   - 后续接入大模型输出时，增加**输出端兜底过滤**，防止大模型幻觉导致直播间被封号。
2. **安全隔离**：
   - 管理端默认绑定监听 `127.0.0.1`，仅限本机 OBS 访问；若跨机器，通过带 Token 的 Nginx 反向代理并配置白名单。
3. **监控健康检查**：
   - 提供 `GET /api/health` 检查 blivedm 连通状态、当前弹幕入库吞吐速率（QPS）、过滤统计及活跃 SSE 客户端数。

## 8. 演进路线图 (Roadmap)
* **M1（接入验证）**：管理端完成 blivedm 直播间连接，控制台结构化输出事件。
* **M2（管线闭环）**：完成多级过滤、同用户冷却、广播队列与背压处理。
* **M3（Web端渲染）**：FastAPI 提供 SSE `/api/stream`，前端页面完成弹幕平滑浮层渲染。
* **M4（OBS生产验证）**：在 OBS / B站直播姬作为浏览器源连续跑通 4 小时压力与稳定性测试。
* **M5（管理控制台）**：开发可视化的 Web 配置面板，支持在线增删违禁词、调整冷却时长。
* **M6（AI 大模型与语音）**：引入 LLM 意图识别与流式回答，集成低延迟 TTS 分句生成与音频推送。
* **M7（虚拟人全驱动）**：引入 Live2D / 3D 虚拟形象，通过口型同步与表情指令实现完整 AI 虚拟主播。
